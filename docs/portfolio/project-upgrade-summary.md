# HUST WORLD 项目升级复盘与简历面试准备

本文档用于总结 HUST WORLD 从课程设计项目升级为可展示、可维护、可写进简历的校园模拟 RPG 作品的过程。内容分为项目概览、阶段成果、关键问题与解决方案、测试质量体系、简历写法和面试问答。后续写简历、准备面试或做项目展示时，可以直接从本文档中提炼。

## 1. 项目定位

HUST WORLD 是一个以华中科技大学校园生活为主题的 Web 校园模拟 RPG。玩家可以创建角色，在校园地图中移动、探索地点、与 NPC 对话、完成任务、加入社团、参加课程、跑步锻炼、触发考试/挑战，并经历从入学到毕业的成长周期。

升级前，这个项目已经有一定的课程设计基础和游戏内容雏形，但整体更接近“能跑的课程作业”。升级目标不是推翻重写，而是在保留原有游戏线和技术栈的前提下，把它逐步打磨成：

- 能稳定启动和演示的 Web 游戏项目。
- 有清晰后端分层、统一 API、健康检查和测试脚本的工程项目。
- 有账号、角色、存档、任务、地图、NPC、成长、背包、技能等完整玩法闭环的 RPG。
- 有统一 UI/UX、可展示截图和自动化验收的作品。
- 能在简历中讲清楚技术难点、工程取舍和个人贡献的项目。

## 2. 技术栈与整体架构

### 2.1 技术栈

- 后端：Node.js、Express、mysql2
- 数据库：MySQL 8.0
- 鉴权：JWT、bcryptjs
- 前端：原生 HTML、CSS、JavaScript
- 游戏表现：Canvas/DOM 混合地图交互
- 测试：Node 脚本、Playwright 浏览器自动化、服务级测试、API 冒烟测试

### 2.2 当前架构

后端已经从原本较松散的路由逻辑整理为分层结构：

- `routes/`：只处理 HTTP 请求和响应。
- `services/`：承载业务逻辑，例如用户、角色、存档、跑步、健康检查。
- `repositories/`：封装数据库访问。
- `middlewares/`：鉴权、错误处理、参数校验。
- `utils/`：统一响应、日志、配置健康检查等工具。

前端也逐步形成了清晰边界：

- `game/js/core/`：存档、会话等核心能力。
- `game/js/config/`：任务、NPC、对话、物品、成长、技能配置。
- `game/js/managers/`：任务触发、成长、背包、技能等管理器。
- `game/js/ui/`：HUD、反馈、对话、面板等 UI。
- `map/js/features/`：地图 POI、NPC、室内场景、任务联动。
- `tools/tests/`：调试页和自动化测试脚本。

## 3. 我的角色与工作方式

如果以后被问“你在项目中具体做了什么”，推荐这样回答：

> 我负责把一个已有课程设计项目从“功能分散、只能局部运行”的状态，逐步升级成一个可展示、可测试、可继续迭代的校园 RPG。我没有直接推翻重写，而是先做工程体检和问题收敛，再按阶段推进：后端分层、账号和存档、主线与支线玩法、地图系统、NPC 对话、任务状态机、成长背包技能、UI 产品化、自动化测试与健康检查。整个过程中，我重点关注模块边界、存档兼容、任务配置化、浏览器真实验收和 UI 重叠问题。

如果需要说明 AI 协作，可以这样讲：

> 这个项目开发过程中我使用 AI Agent 作为辅助工程师，负责根据我的阶段目标执行代码修改和测试。我主要承担需求拆解、路线规划、验收标准制定、问题定位、结果复核和最终整合。遇到数据库、路由、存档、UI 重叠、地图交互丢失等问题时，我会根据现象判断优先级，再要求 Agent 按照现有架构修复，而不是盲目重写。

这个说法比较稳妥，也符合真实协作过程。面试中不要只说“我让 AI 做了”，要强调你主导了目标、边界、验收和取舍。

## 4. 升级阶段总览

### 第一阶段：工程体检与基础修复

目标：先让项目稳定、清晰、可继续开发。

完成内容：

- 全面阅读项目结构，梳理前端、后端、地图、数据库和测试脚本之间的关系。
- 修复 README、HTML、JS、CSS 中的中文显示问题。
- 检查 Express 路由顺序，避免 `/:id` 抢先匹配更具体的接口。
- 统一数据库字段命名，例如 `npc_function` / `npcfunction` 这类历史不一致字段。
- 统一 API 返回格式为 `{ success, data, message }` 或 `{ success: false, error }`。
- 创建 `.env.example`，补充数据库、端口、JWT、测试地址等配置说明。
- 新增 `/api/health` 健康检查接口。
- 重写 README 的安装、数据库配置、启动和测试说明。
- 建立 API 冒烟测试和测试数据清理脚本。

遇到的问题：

- 项目文档和代码存在中文乱码，影响维护和展示。
- 路由顺序存在潜在冲突，某些接口可能被动态路由误匹配。
- API 返回格式不统一，前端和测试脚本需要写大量特殊判断。
- 本地数据库启动方式不清晰，新同学接手成本高。

解决思路：

- 先修“影响后续开发的基础问题”，不急着做新功能。
- 通过 `.env.example` 和 README 固化启动流程。
- 用健康检查和冒烟测试确认项目不是“看起来能跑”，而是真的可用。

### 第二阶段：架构整理与模块边界

目标：让后端结构更接近真实工程。

完成内容：

- 将后端拆分为 `routes / services / repositories / middlewares / utils`。
- 统一错误处理中间件、参数校验、日志和响应格式。
- 创建 JWT 鉴权中间件。
- 将 `/api/init` 等逻辑迁移到 service 层。
- 对 `maps`、`npcs`、`tasks`、`items`、`skills`、`clubs`、`exploration`、`running` 等 routes 进行响应格式收口。
- 最小拆分 running 模块，形成 repository + service + route。
- 新增 `cleanup:smoke` 命令，清理测试用户和关联数据。

遇到的问题：

- 很多业务逻辑直接写在 route 中，导致难以测试和复用。
- 测试数据会积累在数据库中，影响后续冒烟测试。
- README 中端口说明和脚本默认值曾经不一致。

解决思路：

- 先做“最小可用分层”，不一次性大重构。
- 新增业务时优先走 service/repository，新旧模块逐步迁移。
- 将测试数据统一用 `smoke_user_` 等前缀命名，并提供清理脚本。

### 第三阶段：账号、角色与存档系统

目标：实现真正可以持续游玩的账号和存档闭环。

完成内容：

- 扩展 `characters` 表，新增 `mood`、`current_map_id`、`position_x`、`position_y`、`updated_at`、`last_saved_at` 等字段。
- 使用 `game_progress JSON` 存储复杂游戏进度，避免频繁改表。
- 新增角色存档 API：
  - `GET /api/character/:id/save`
  - `PUT /api/character/:id/save`
  - `POST /api/character/:id/save/reset`
- 新增 `SaveManager`，支持：
  - 游客 localStorage 存档
  - 登录用户远程数据库存档
  - 自动保存
  - 手动保存
  - 重置存档
  - 旧存档迁移
- 新增 `SessionManager`，统一管理 token、user、角色列表、当前角色 ID。
- 开始界面区分游客、本地存档、登录用户有角色、登录用户无角色等状态。
- 新增浏览器调试页 `test-save-manager.html`。

遇到的问题：

- 存档接口曾出现 404，排查后发现需要确认路由注册顺序和服务器是否重启。
- 前端存在游客模式和登录模式切换混乱的问题。
- 登录后刷新页面时 `currentCharacterId` 丢失，导致 SaveManager 误以为是游客模式。
- 旧 localStorage key 会覆盖新存档。
- `SaveManager.js` 一度存在 ES Module 与普通 `<script>` 引入方式不兼容的问题。

解决思路：

- 后端用统一的角色存档 API 封装数据库字段和 `game_progress`。
- 前端将“会话”和“存档”拆成两个管理器，避免 token、角色、存档混在一起。
- 登录模式必须同时具备 token 和 currentCharacterId 才走远程存档。
- 旧存档迁移成功后删除旧 key，避免重复覆盖。
- 兼容浏览器全局引入和 Node 测试环境，保证调试页和自动化测试都能加载。

面试可以这样说：

> 存档系统我没有简单地把所有字段都塞进 localStorage，而是设计了游客和登录用户两套模式。游客使用 localStorage，登录用户使用后端角色存档接口。基础属性保留在 characters 表中，复杂进度放在 game_progress JSON 中，这样既能查询角色基础信息，也能灵活保存任务、背包、技能、NPC 对话历史等复杂状态。

### 第四阶段：核心玩法闭环

目标：让游戏从“功能集合”变成“有主线、有支线、有成长目标”的可玩流程。

完成内容：

- 基于已有 `QuestTriggerConfig.js`、`QuestTriggerManager.js`、`QuestTriggerUI.js`、`DialogueConfig.js`、`TimeSystem.js`、`SaveManager.js` 继续增强，没有新建平行主线系统。
- 打通大一上学期主线：
  - 新生报到
  - 军训
  - 宿舍休息
  - 高数入门
  - 图书馆自习
  - 期末考试
  - 阶段总结
- 补齐大一下到大四的学期推进和总结任务。
- 新增 `ExamChallengeAdapter`，根据 knowledge、高等数学熟练度、mood、stamina 计算考试结果。
- 新增社团、跑步、探索三条支线链，每条从 freshman 到大四逐步解锁。
- 任务进度接入 SaveManager，完成、激活、阶段推进后自动保存。
- 新增主线和支线浏览器自动化测试。

遇到的问题：

- 任务触发逻辑中出现 `prereqMet` 未定义的运行时错误。
- `/game/index.html` 曾经 404，需要补充静态路由。
- 主线任务完成从同步变成异步后，需要兼容考试挑战这种异步流程。
- 测试页面路径和自动打穿逻辑曾经不稳定。

解决思路：

- 不推翻原有任务系统，而是围绕现有 QuestTrigger 系列模块增强。
- 把考试挑战封装成 Adapter，让任务完成逻辑可以等待异步结果。
- 用浏览器自动化脚本真实打穿主线，而不是只测函数返回。

面试可以这样说：

> 这个阶段的重点不是写更多剧情文本，而是把剧情、任务、时间、属性和存档连起来。比如期末考试不是固定成功，而是由知识、心情、体力和课程熟练度共同影响结果，失败后可以重试，这样游戏才有成长反馈。

### 第五阶段：地图系统升级

目标：让地图成为游戏核心入口，而不是一张静态背景。

完成内容：

- 将 POI 与任务、NPC、室内场景绑定。
- 地点面板显示 POI 信息、关联 NPC、可接任务、进行中任务和可交付任务。
- 支持室内场景，例如宿舍、图书馆、教学楼、食堂、实验室、社团活动中心等。
- 地图任务标记区分可接、进行中、可交付、已完成和追踪状态。
- 支持任务追踪定位。
- 修复地图缩放、移动、图层残留、旧文字叠层等 UI 问题。
- 添加小地图功能：显示 POI、玩家位置、视野框、缩放倍率，支持点击定位和折叠。
- 恢复并验证 `按 E 乘坐巴士` 交互。

遇到的问题：

- 地图页面曾经出现图层下方残留“打卡列表”等旧调试内容。
- 地图缩放范围没有限制时，容易出现画面失控和控件错位。
- UI 全面改造后，原本的巴士和 NPC 交互入口一度被隐藏或断开。
- 多个侧栏、HUD、时间栏、当前位置模块出现重叠。

解决思路：

- 清理旧调试 DOM 和重复脚本加载。
- 将地图层、HUD 层、小地图层、面板层的 z-index 和布局边界重新整理。
- 增加 UI 几何重叠测试，自动检查桌面和移动端关键区域是否重叠。
- UI 改造后必须跑地图交互测试，避免“看起来更美但功能丢失”。

面试可以这样说：

> 地图系统升级中我遇到的典型问题是 UI 重构容易影响原有交互。比如巴士和 NPC 原来是可用的，但新界面覆盖后入口不明显甚至失效。我后来把地图交互纳入自动化测试，包括 POI、室内场景、NPC、巴士和小地图，避免单纯依赖人工点点看。

### 第六阶段：NPC 与对话系统

目标：让 NPC 成为剧情、任务、商店和地图交互的入口。

完成内容：

- 新增和完善 `NpcConfig.js`，配置迎新志愿者、军训教官、高数老师、图书馆管理员、社团负责人、跑步教练、实验室导师、商店 NPC 等。
- 升级 `DialogueConfig.js`，支持结构化多轮对话、条件分支、任务触发、任务交付、商店入口和社团入口。
- 新增 `NpcDialogueUI.js`，支持 NPC 名称、身份、地点、正文、选项按钮、关闭按钮、任务状态、奖励展示和商店购买。
- 新增 `ItemConfig.js`，配置饭卡套餐、咖啡、笔记本、运动饮料、社团纪念章、实验室通行证等商品。
- 地图和室内场景支持 NPC 标记、靠近提示、点击交谈。
- SaveManager 扩展 `npcRelations` 和 `npcDialogueHistory`。
- 最新补充 NPC 头像/图标标记，让地图上的 NPC 更直观可见。

遇到的问题：

- 早期调试页加载失败，原因是模块加载方式不统一。
- 商店购买后金币和背包需要立刻刷新并持久化。
- 如果 SaveManager 或 questManager 不存在，页面不能白屏。
- UI 改造后玩家反馈“看不到 NPC”，说明视觉标记不够明显。

解决思路：

- 对话系统继续复用现有配置，不另起一套平行系统。
- UI 组件做安全兜底：缺少管理器时仍可显示基础对话。
- 商店购买后同时更新角色状态、背包数据、HUD，并调用 SaveManager 保存。
- 地图 NPC 增加头像式标记、状态点和 tooltip，提高可发现性。

面试可以这样说：

> NPC 系统我主要做了配置化和联动。NPC 不只是显示一句话，而是和任务、地点、商店、社团、关系值、存档历史绑定。这样后续新增 NPC 时，主要补配置和对话分支，而不是复制一堆 UI 逻辑。

### 第七阶段：任务系统升级

目标：把任务系统从“能触发”升级为可配置、可维护、可测试的产品化任务系统。

完成内容：

- 统一任务字段：
  - `id`
  - `title`
  - `description`
  - `type`
  - `category`
  - `phase`
  - `locationId`
  - `sceneId`
  - `npcId`
  - `poiId`
  - `prerequisites`
  - `objectives`
  - `rewards`
  - `unlocks`
  - `recommendedStats`
  - `timeCost`
  - `staminaCost`
  - `repeatable`
  - `hidden`
  - `priority`
  - `tags`
- 统一任务状态：
  - `LOCKED`
  - `AVAILABLE`
  - `ACTIVE`
  - `READY_TO_COMPLETE`
  - `COMPLETED`
  - `FAILED`
  - `EXPIRED`
- 支持接取、推进、完成、奖励、解锁和追踪。
- 任务日志支持分类 Tab、状态标签、目标进度、奖励、地点、NPC、前置条件、追踪和地图定位。
- 任务与 NPC 对话、地图 POI、室内场景、奖励系统、物品系统打通。
- 新增 `test-quest-system.html` 和 `npm run test:quest`。

遇到的问题：

- 旧任务字段不统一，不同主线/支线结构差异大。
- 任务完成、奖励发放、地图标记、NPC 对话之间容易状态不同步。
- 任务日志信息很多，容易出现文字重叠和信息层级混乱。

解决思路：

- 先统一任务模型，再做 UI 展示。
- 将奖励发放和状态流转集中到任务管理器中，减少各模块自行修改进度。
- 任务日志 UI 做分类和详情区，不把所有信息堆在一个卡片里。

面试可以这样说：

> 我把任务系统抽象成一个轻量状态机。每个任务都有统一字段和状态，地图、NPC 和任务日志都读取同一份进度数据。这样可以避免一个任务在日志里显示未完成，但 NPC 那边又能交付的状态不一致问题。

### 第八阶段：成长、背包和技能系统

目标：让角色成长有反馈，玩家行为能改变角色能力。

完成内容：

- 新增 `GrowthConfig.js`，统一属性成长、经验、等级、升级奖励和边界。
- QuestTriggerManager 增加统一属性入口和连续升级能力。
- SaveManager 保存成长字段，并兼容旧 `physical` 字段。
- 新增背包系统：
  - `progress.inventory`
  - 物品分类
  - 物品效果
  - 可堆叠/不可堆叠
  - 使用物品
  - 商店购买
  - 任务奖励
- 新增技能和熟练度系统：
  - `progress.skills`
  - 技能解锁
  - 技能升级
  - 技能经验溢出处理
  - 考试、跑步、社交、探索加成
- 完成成长、背包、技能与任务、NPC、地图场景的联动和平衡。
- 新增 `test:growth`、`test:inventory`、`test:skills`、`test:linkage`。

遇到的问题：

- 旧存档里存在 `physical`、`items`、`inventoryCounts`、`unlockedSkills`、`proficiencies` 等历史字段。
- 成长、背包、技能如果各自保存，很容易互相覆盖进度。
- 浏览器测试中一度出现 `QuestTriggerManager is not a constructor`，原因是模块导入方式不匹配。

解决思路：

- SaveManager 做旧字段迁移，保证老存档仍能打开。
- 所有成长、背包、技能数据统一进入 `progress`，由 SaveManager 统一保存。
- 测试脚本统一通过项目 npm scripts 执行，避免直接调用底层测试工具造成误用。

面试可以这样说：

## 5. 关键问题与可讲述解决方案

### 5.1 为什么不推翻重写？

回答思路：

> 因为原项目已经有地图、任务、NPC、课程设计文档和部分游戏线，完全重写会丢掉已有业务理解，也会带来新的风险。我选择增量升级：先修基础问题，再做架构分层，然后围绕已有系统增强。这样每个阶段都能运行、测试和提交，风险更可控。

### 5.2 数据库连不上怎么办？

项目中真实遇到过 MySQL 密码错误、服务未启动、3306 拒绝连接等问题。

处理方式：

- 使用 `/api/health` 判断数据库状态。
- 使用 `check:config` 单独检查配置。
- 明确 `.env` 中的 `DB_HOST`、`DB_USER`、`DB_PASSWORD`、`DB_NAME`。
- 数据库不可用时允许服务降级启动，方便前端调试。
- 测试数据使用固定前缀，执行后可清理。

面试回答：

> 我没有把数据库问题简单隐藏掉，而是把它变成可观测状态。服务可以降级启动，但 health 接口会明确返回 database error，配置检查脚本会提示是端口、密码、主机还是服务状态问题。

### 5.3 如何设计存档系统？

回答重点：

- 游客模式和登录模式分离。
- 游客用 localStorage。
- 登录用户用后端 save API。
- 基础字段放 characters 表。
- 复杂进度放 game_progress JSON。
- SaveManager 统一 load/save/autoSave/reset/migrate。
- SessionManager 管 token、user、角色。

示例回答：

> 我把存档分成两层：会话层和存档层。SessionManager 只管用户是谁、token 是什么、当前角色是谁；SaveManager 只管游戏进度如何加载和保存。这样登录状态变化不会直接污染存档逻辑。后端则用 characters 表保存基础属性，用 game_progress JSON 保存任务、背包、技能、NPC 历史等复杂状态。

### 5.4 任务系统如何避免混乱？

回答重点：

- 统一任务字段。
- 统一状态机。
- 任务奖励集中发放。
- 地图、NPC、任务日志都读同一份进度。

示例回答：

> 我把任务抽象成配置 + 状态机。任务配置描述前置、目标、奖励、地点、NPC；任务状态机负责 LOCKED、AVAILABLE、ACTIVE、READY_TO_COMPLETE、COMPLETED 等状态流转。这样 NPC、地图和任务日志不需要各自判断一套逻辑，减少状态不一致。

### 5.5 UI 重叠和功能丢失怎么解决？

回答重点：

- 重叠问题通过布局边界和测试解决。
- 功能丢失通过回归测试解决。
- UI 不是只看截图，还要测试真实交互。

示例回答：

> 我遇到过 HUD、时间栏、任务卡片、地图控件互相重叠的问题。后来我把布局拆成固定区域和独立滚动面板，并增加浏览器几何测试，自动检查关键元素是否重叠。同时 UI 改造后补跑地图、NPC、任务测试，避免巴士、NPC 对话这类交互被新界面遮住。

### 5.6 如何解释 AI Agent 参与？

推荐回答：

> 我把 AI Agent 当成开发助手，而不是替代我做决策。我的工作重点是拆阶段、定验收标准、判断问题优先级、检查结果和调整方向。比如做 UI 时，我会指出“任务卡片重叠”“NPC 不可见”“巴士入口丢失”这些真实问题，再让 Agent 基于现有代码修复并跑测试。这个过程更像我在做产品和工程负责人，Agent 辅助完成具体代码实现。

## 8. 面试高频问题与回答

### Q1：这个项目最大的难点是什么？

可以回答：

> 最大难点是系统之间的联动和兼容。这个项目不是单独做一个页面，而是账号、角色、存档、任务、地图、NPC、背包、技能和 UI 都要互相影响。比如 NPC 对话可能触发任务，任务完成会发奖励，奖励会改变背包和角色属性，地图上还要更新任务标记，最后这些都要保存。我的解决方式是统一进度数据和任务状态机，让各模块围绕同一套 progress 和配置工作。

### Q2：你为什么使用原生 JavaScript，而不是 Vue/React？

可以回答：

> 这个项目原始技术栈就是原生 HTML/CSS/JS，我的目标是把已有课程设计升级成稳定作品，而不是为了换框架重写。保留原生技术栈可以减少迁移成本，也更能体现我对 DOM、模块边界、状态管理和浏览器测试的理解。后续如果继续做产品化，可以再考虑用 Vue 或 React 重构前端。

### Q3：后端分层做了什么？

可以回答：

> 我把原来直接写在 route 里的逻辑拆到 service 和 repository。routes 只处理请求响应，services 处理业务规则，repositories 负责数据库访问。这样 API、业务逻辑和数据访问的边界更清楚，也方便做服务级测试，比如 authService、characterService、runningService 都能单独验证。

### Q4：存档为什么用 JSON？

可以回答：

> 因为游戏进度变化很快，任务、背包、技能、NPC 历史、成就都属于结构复杂、迭代频繁的数据。如果每加一个字段都改表，维护成本会很高。所以我把角色基础信息放在 characters 表字段里，把复杂进度放到 game_progress JSON。这样既保留了基础字段查询能力，也保留了游戏内容扩展的灵活性。

### Q5：怎么保证 UI 改造没有破坏功能？

可以回答：

> 我补了浏览器自动化测试和 UI 几何测试。比如地图、NPC、任务、背包、技能都有专项测试，UI 布局测试会检查关键模块是否重叠，响应式测试会检查移动端是否水平溢出。每次 UI 改造后，不只看截图，还会跑交互测试，比如 NPC 能否打开对话、商店能否购买、任务能否接取和完成。

### Q6：项目中最有代表性的 bug 是什么？

可以回答：

> 有几个比较典型。一个是登录后刷新页面 currentCharacterId 丢失，导致 SaveManager 误走游客模式；我通过 SessionManager 恢复当前角色并严格判断 token + characterId 才走远程模式。另一个是 UI 改造后巴士和 NPC 交互入口消失，我发现是新界面层级和旧交互没有接好，后来恢复了地图交互绑定，并加测试防止回归。

### Q7：你如何处理数据库环境问题？

可以回答：

> 我遇到过 MySQL 密码、服务未启动和端口拒绝连接的问题。后来我补了 `/api/health` 和 `check:config`，让服务启动和测试时能明确告诉我数据库是正常、拒绝连接、密码错误还是端口问题。数据库不可用时服务可以降级启动，保证前端调试不中断，但健康检查会明确显示 database error。

## 11. 一分钟项目介绍

可以这样讲：

> HUST WORLD 是我参与升级的一个校园模拟 RPG 项目，技术栈是 Node.js、Express、MySQL 和原生 JavaScript。项目以华中科技大学校园生活为背景，玩家可以创建角色，在地图中探索地点、和 NPC 对话、完成主线支线任务、加入社团、跑步锻炼、参加考试，并通过背包和技能系统成长。我主要做的是把原本课程设计性质的项目工程化和产品化：后端做了分层、统一 API 和健康检查，前端做了 SaveManager、SessionManager、任务状态机、地图/NPC/背包/技能联动和 UI 产品化，最后补了 Playwright 浏览器测试、服务级测试和 quick/standard/full 测试矩阵。这个项目最有价值的地方是系统联动比较完整，不只是单个页面，而是一个可持续迭代的 Web 游戏作品。

## 12. 三分钟项目介绍

可以这样讲：

> 这个项目最开始是一个课程设计，有校园 RPG 的主题和部分基础功能，但工程结构、存档、任务、地图、NPC、UI 和测试都比较分散。我没有选择推翻重写，而是先做工程体检和基础修复，包括中文乱码、路由顺序、API 返回格式、环境变量和健康检查。之后把后端拆成 routes、services、repositories、middlewares、utils，让业务逻辑和数据库访问分开。
>
> 在玩法层面，我先做账号、角色和存档系统。游客用 localStorage，登录用户用后端角色存档接口，复杂进度存到 game_progress JSON，SaveManager 负责加载、保存、自动保存和旧存档迁移，SessionManager 负责 token、用户和当前角色。然后我在已有任务系统基础上增强主线和支线，实现大学四年推进、社团、跑步、探索、考试挑战、任务日志和地图追踪。
>
> 后面我继续做了地图、NPC、任务系统升级。地图支持 POI、室内场景、NPC 标记、小地图和巴士交互；NPC 支持多轮对话、任务触发、任务交付和商店购买；任务系统统一字段和状态机，地图、NPC 和任务日志都读取同一份进度。第八阶段加入成长、背包和技能系统，让任务奖励真正影响角色属性、物品和熟练度。
>
> 最后我做 UI/UX 产品化和测试质量收口。UI 上统一了主题、按钮、HUD、面板、任务日志、NPC 对话、小地图和响应式布局，并修复了很多重叠问题。测试上补了 API 冒烟、服务级测试、浏览器 E2E、UI 布局测试和 quick/standard/full 三档测试矩阵。现在这个项目可以作为一个可演示、可继续迭代、可写进简历的完整 Web 游戏作品。
